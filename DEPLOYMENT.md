# Deploying S2VESTIS

You already have a **Supabase** project with the schema applied (see
[`supabase/README.md`](supabase/README.md)) — deploying just points **Render**
(API) and **Vercel** (frontend) at it, ~10 minutes. Vercel proxies `/api/*` to
Render (via [`client/vercel.json`](client/vercel.json)), so the browser only
ever talks to your Vercel domain — the login cookie stays same-site with
**zero backend changes**. This mirrors the dev-time Vite proxy exactly.

```
Browser → yourapp.vercel.app
            ├─ /            → static SPA (Vercel)
            ├─ /api/*       → proxied to → s2vestis-api.onrender.com/api/*
            └─ /uploads/*   → proxied to → s2vestis-api.onrender.com/uploads/*
                                              │
                                              └─ Supabase (Postgres)
```

> Prefer a single Render service instead of splitting front/back? See
> [Alternative: one service](#alternative-one-service) at the bottom.

## 1. Database — Supabase

Already set up locally? Reuse the same project — grab **Project URL** and the
**`service_role`** key from Project Settings → API (same values as in your
local `server/.env`). Starting fresh: see [`supabase/README.md`](supabase/README.md)
to create a project and apply the migrations first.

## 2. Backend — Render

1. Push this repo to GitHub if you haven't (`git push`).
2. [dashboard.render.com](https://dashboard.render.com) → **New → Blueprint** → connect the repo.
   Render reads [`render.yaml`](render.yaml) at the repo root and proposes a
   `s2vestis-api` web service rooted at `server/`.
3. Before the first deploy, fill in the env vars it leaves blank (**Environment** tab):
   | Key | Value |
   | --- | --- |
   | `SUPABASE_URL` | your project URL from step 1 |
   | `SUPABASE_SERVICE_ROLE_KEY` | the `service_role` key from step 1 — treat as a secret |
   | `CLIENT_URL` | your Vercel URL — you'll know it after step 3.2 below; put a placeholder like `https://s2vestis.vercel.app` for now and correct it once Vercel assigns the real one |
   | `SEED_ADMIN_PASSWORD` / `SEED_USER_PASSWORD` | pick real passwords (only used if you run the seed) |
   | `CLOUDINARY_*` (optional) | from [cloudinary.com](https://cloudinary.com) free tier — recommended, see [Image uploads](#image-uploads-render-disk-is-ephemeral) |

   `JWT_SECRET` is auto-generated by the blueprint. Leave it as-is.
4. Deploy. Once live, note the URL — something like `https://s2vestis-api.onrender.com`.
5. Check it: open `https://s2vestis-api.onrender.com/api/health` → should return `{"success":true,"status":"ok",...}`.

**Load demo data** (8 categories, ~33 products, admin + demo user) — from your machine, once, against the *same* Supabase project (reuses `server/.env`):
```bash
cd server && npm run seed
```
⚠️ This wipes and reloads all data in that Supabase project — the same project your local dev server and Render both point at.

## 3. Frontend — Vercel

1. Open [`client/vercel.json`](client/vercel.json) and replace **both**
   `REPLACE_WITH_RENDER_URL.onrender.com` occurrences with your real Render
   hostname from step 2.4. Commit and push that change.
2. [vercel.com/new](https://vercel.com/new) → import the repo → set **Root Directory** to `client`.
   Vercel auto-detects Vite (`npm run build`, output `dist`) — no other settings needed.
3. Deploy. Vercel gives you a URL like `https://s2vestis-<hash>.vercel.app`
   (or set a cleaner one in **Settings → Domains**).
4. Go back to Render (step 2.3) and set `CLIENT_URL` to this exact URL, then
   **Manual Deploy → Deploy latest commit** to restart the API with it.

## 4. Verify

Visit your Vercel URL:
- Home page loads, categories/products appear (confirms the Vercel → Render
  proxy and Atlas connection both work).
- Register or log in as `admin@s2vestis.com` (or whatever `SEED_ADMIN_PASSWORD`
  you set) → cart/wishlist icons should reflect state after reload (confirms
  the auth cookie is being set and sent correctly).
- `/admin` → dashboard shows real counts.

If login "succeeds" but you're logged out on refresh: `CLIENT_URL` on Render
doesn't exactly match your Vercel URL, or `client/vercel.json` still has the
placeholder hostname — fix and redeploy both.

## Image uploads: Render disk is ephemeral

Without Cloudinary configured, admin-uploaded images fall back to
`server/uploads/` on Render's filesystem, which is **wiped on every deploy**.
For anything beyond a demo, set the three `CLOUDINARY_*` env vars on Render
(free tier is plenty) — the app already switches to it automatically when
they're present (see [`server/README.md`](server/README.md)).

## Costs & limits (free tiers)

- **Render free web service** sleeps after 15 minutes idle; the first request
  after that takes ~30–50s to wake up. Fine for a demo; upgrade to a paid
  instance ($7/mo Starter) to remove the cold start.
- **Supabase free tier** — 500MB database, plenty for this catalogue.
- **Vercel Hobby** — generous bandwidth/build limits for a project this size.

## Alternative: one service

If you'd rather not split front/back (and don't mind losing Vercel's edge
CDN), point `server/src/app.js` at `client/dist` with
`express.static(...)` + a catch-all to `index.html`, build the client into
`server/client-dist` as part of the Render build command, and deploy only the
Render service. Cookies are then trivially same-origin since there's only one
domain. Ask if you want this wired up instead — it's a small change.
